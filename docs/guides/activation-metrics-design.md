# Opt-in Activation Metrics Design

Status: AG-02 measurement contract. No SDK telemetry is implemented. Landing-page
navigation never counts as install or activation.

## Goal

Understand where new users get stuck in the local AgentGuard path without
weakening the SDK's zero-dependency, local-first promise.

The useful activation question is narrow: can a developer get from install to a
local guard proof without confusion?

## Metric classes (keep these separate)

| Class | Definition | What it is not |
|---|---|---|
| Page navigation | Site views, unique viewers, CTA clicks, AI crawls, bot views | Install, activation, or repeat use |
| Install | PyPI `without_mirrors` package events in a **calendar** UTC window, after labeling publication/CI bursts | Unique users, successful first run |
| Install intent | bmdpat events whose **target** is the PyPI project URL or a copied `pip install agentguard47` command | Landing-page hits named `install_intent` |
| Guard activation | A consented demo-feedback report or GitHub issue using `.github/ISSUE_TEMPLATE/activation_feedback.yml` with `result=success` | A download, clone, or page view |
| Repeat use | The same consented reporter on two calendar days inside 14 days | Two PyPI downloads |
| Accepted contribution | A merged PR from an author who is not a repo collaborator, or an issue accepted into the backlog | Stars, forks, or subscriber signups |

North-star from [#729](https://github.com/bmdhodl/agent47/issues/729): external
repeat users with a consented reproduction of a useful guarded workflow.

## Baseline snapshot

The dated snapshot is
[activation-baseline-2026-09-18.json](activation-baseline-2026-09-18.json).
Regenerate a weekly aggregate with:

```bash
python scripts/activation_weekly_report.py docs/guides/activation-baseline-2026-09-18.json
```

The script is offline by default. It never scrapes identities. Unknowns stay
unknown. Publication dates and CI clones are exclusions, not users.

Exact query windows, dedup rules, and unknowns live in that JSON. As of
2026-09-18:

- PyPI `without_mirrors` 7d ending 2026-09-17: 266 package events. 241 (90.6%)
  fell on publication burst days 2026-09-12 and 2026-09-15.
- npm `@agentguard47/mcp-server` 2026-08-19 through 2026-09-17: 144 downloads.
- GitHub traffic in the parent readback: 49 views / 38 unique viewers;
  1,411 clones / 271 unique cloners. Clones include CI.
- Site events 2026-08-19 through 2026-09-18: 375 views, 180 AI-crawl, 85 bot
  views, 2 CTA clicks, 2 `install_intent` events **both targeting the landing
  page** → 0 proven installs from those events.
- 7 active subscribers. Signups are interest, not activation.

## Voluntary demo feedback

After `agentguard demo`, the CLI prints how to inspect a redacted report.
`agentguard demo --feedback` prints only `version`, `adapter`, `result`, and
`reproduction`. The user can `--omit` fields, edit the text, or decline by
skipping the command. The demo makes no network call.

Share path: paste into
[the Demo feedback issue template](../../.github/ISSUE_TEMPLATE/activation_feedback.yml)
after inspecting it. Opening the issue is the user's action, not the SDK's.

## Questions Worth Answering

- Do users reach `agentguard doctor` after install?
- Does `agentguard doctor` complete successfully?
- Do users run `agentguard demo` or `agentguard quickstart` after doctor?
- Which framework quickstart is most often selected?
- Do hosted ingest contracts accept or reject events by SDK version?
- Which documented steps produce errors often enough to fix?

Answer these with server-side stores and consented reports first. Do not
instrument local-only users to manufacture the signal.

## Explicit Consent Model

No telemetry should run by default.

If implemented later, consent must be explicit at the command boundary:

- one-shot CLI flag, such as `--share-activation-metrics`
- environment opt-in, such as `AGENTGUARD_SHARE_METRICS=1`
- repo-local opt-in in `.agentguard.json`, never generated by default

Every opt-in path should print what will be sent before sending anything.
AG-02 does **not** implement that network path.

## Allowed Fields

Only coarse activation metadata is allowed:

- SDK version
- Python major/minor version
- operating system family
- command name, such as `doctor`, `demo`, or `quickstart`
- command result: success or failure
- framework choice for `quickstart`
- anonymous random install/session id generated only after opt-in
- coarse error category, such as `import_error`, `trace_write_failed`, or
  `invalid_framework`

The demo feedback report is stricter: version, adapter, result, reproduction.

## Forbidden Fields

Never collect:

- trace payloads
- prompts, completions, code, diffs, stack traces, or tool arguments
- API keys, secrets, environment variables, or headers
- filesystem paths, repo names, usernames, hostnames, or IP addresses
- `.agentguard.json` contents
- model inputs, model outputs, token text, or provider request bodies
- dashboard project names or customer identifiers
- scraped identities, subscriber emails, or unsanctioned outreach lists

If a field can identify a person, repo, machine, project, or agent payload, it
does not belong in SDK activation metrics.

## Server-side Metrics First

Prefer metrics that do not require SDK telemetry:

- PyPI downloads by version
- GitHub clone/view/referrer data
- docs page views and outbound clicks
- hosted ingest counters by SDK version and accepted/rejected event kind

These answer adoption questions without instrumenting local-only users.

## Zero-dependency Transport

If implemented later, the SDK must use only the Python standard library. Any
network call must be bounded:

- short timeout
- no retries by default
- failure is silent or logged at debug level
- never blocks or crashes the guarded agent

Metrics transport must be separate from `HttpSink` so trace ingestion and
activation metrics do not become confused.

## Kill Switch

Any future implementation needs a hard off switch:

- `AGENTGUARD_DISABLE_METRICS=1` wins over all opt-ins
- metrics endpoint can reject or disable metrics without affecting SDK behavior
- package behavior stays identical when metrics fail

## Recommended First Implementation

AG-02 ships documentation, the weekly classifier, the issue template, and
local demo feedback. It does not send metrics.

If local SDK metrics are still needed later, add one opt-in CLI-only experiment
for `agentguard doctor` and `agentguard quickstart`. Do not instrument imports,
guards, tracing, sinks, or normal application runtime.

## Non-goals

- no default telemetry
- no runtime agent instrumentation
- no trace sampling
- no dashboard-required SDK behavior
- no dependency additions
- no product analytics hidden inside local guard execution
- no new subscriber store, scraped identities, cold outreach, or unsanctioned email
- landing-page navigation never counts as install
